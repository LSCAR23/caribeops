# Business Entity Design

This document defines the proposed PostgreSQL structure for a CaribeOps business before the businesses migration is created.

## Domain meaning

Each business belongs to one broad **category**, represented by `category_id` (for example, Hotel, Restaurant, or Tour). Its `type` describes the more specific kind of business within that category (for example, Boutique hotel, Hostel, Café, or Snorkeling tour). The category is stored as a foreign key rather than repeated as a text label on every business.

## Business columns

| Column | PostgreSQL type | Nullable | Meaning and constraints |
|---|---|---:|---|
| `id` | `bigint` identity | No | Generated primary key. |
| `category_id` | `bigint` | No | Foreign key to `categories.id`; a business must belong to a broad category. The delete policy is to be selected with the categories/businesses migrations. |
| `name` | `varchar(255)` | No | Business display name. |
| `description` | `text` | No | Business description. |
| `type` | `varchar(120)` | No | Specific kind of business. Kept as text, not a database enum, in this initial design. |
| `address` | `text` | No | Required displayable address. |
| `latitude` | `numeric(10,7)` | No | Decimal latitude; constrain values to the inclusive range -90 through 90. |
| `longitude` | `numeric(10,7)` | No | Decimal longitude; constrain values to the inclusive range -180 through 180. |
| `website` | `text` | Yes | Optional website URL. URL-format validation is an application/API responsibility. |
| `phone` | `varchar(32)` | No | Phone number stored as text to preserve a leading `+` and formatting. |
| `created_at` | `timestamp` | No for persisted rows | System-managed creation time, not a value a user must provide when creating a business. |
| `updated_at` | `timestamp` | No for persisted rows | System-managed last-update time, not a value a user must provide when creating a business. |

`numeric(10,7)` stores decimal values exactly at the selected precision. The coordinate range constraints reject out-of-range locations; they do not validate address consistency or whether a location is on land.

## Requiredness

Among user-provided business attributes, only `website` may be absent when a business is created. The primary key and timestamps are generated by the system. `category_id` is required to maintain the category relationship.

## Relationship and migration notes

- `businesses.category_id` references the primary key `categories.id`, giving the domain relationship Category 1-to-many Business.
- The category deletion policy is intentionally left for the categories/businesses migration design; do not assume cascading deletion without deciding whether deleting a category with businesses should be permitted.
- When implementing Laravel timestamps, confirm that the migration enforces the documented non-null requirement for persisted records. Laravel's conventional timestamp helper may create nullable timestamp columns.
- The chosen string bounds and coordinate precision are initial design recommendations. Revisit them only if concrete domain or validation requirements call for different limits.
